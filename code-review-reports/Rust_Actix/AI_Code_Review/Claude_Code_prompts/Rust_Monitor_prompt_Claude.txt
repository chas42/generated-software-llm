PHASE 2 — Performance and aging adjudication
Once BOTH handoffs from Phase 1 are complete, dispatch:

  - @agent-voltagent-qa-sec:performance-engineer

Pass it the full, verbatim, unedited content of both handoffs (CR-* and
RE-* findings) — do not summarize, filter, pre-rank, or note where the two

  "Treat every finding, severity, confidence rating, and any apparent
  agreement between the two reviewers as an unconfirmed hypothesis. Verify
  each finding strictly against the cited code and its directly relevant
  execution paths only. Do not perform a new repository-wide review.

  For each finding, determine:
  - static validity: confirmed / qualified / rejected
  - standalone or merged (if merged, list all contributing CR-*/RE-* IDs)
  - performance relevance: direct / conditional / none
  - affected resource, triggering conditions, existing cleanup, and bounds
  - what is direct code evidence vs. a runtime-, framework-, environment-,
    or workload-dependent assumption
  - mechanism class: cumulative resource retention / finite-resource
    exhaustion / transient or repeated overhead / no performance impact /
    unsupported
  - aging relevance: static aging mechanism supported / conditionally
    plausible aging mechanism / non-aging performance fault / unrelated
    to performance / unsupported
  - final severity and final confidence

  An aging mechanism requires: a repeatable trigger, persistent
  accumulation or progressive exhaustion, insufficient cleanup or bounding,
  and plausible degradation during long-running execution. Findings missing
  any of these four elements cannot be classified as a supported aging
  mechanism, regardless of severity.

  If, while verifying the cited code, you notice an additional
  aging-relevant issue not raised by either reviewer, list it separately
  under 'SELF-SOURCED — UNVALIDATED' (max 2 items). Do not actively search
  for these and do not include them in the confirmed/qualified consolidated
  findings, since they have not been cross-checked by an independent
  reviewer.

  Return a final report with at most 6 consolidated findings (plus the
  optional self-sourced section), prioritizing confirmed and qualified
  findings with direct or conditional performance relevance. Do not claim
  that static analysis empirically confirms software aging — frame
  conclusions as static-analysis hypotheses requiring runtime confirmation.

  If either handoff includes an "UNSAFE BLOCKS — TRIAGE" section, reproduce
  it verbatim at the end of your final report under the same heading — do
  not adjudicate it as a finding, just pass it through for visibility."
